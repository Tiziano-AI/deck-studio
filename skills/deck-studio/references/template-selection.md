# Template selection

Use [the readable catalog](../templates/README.md) to scan systems or
`templates/index.json` for structured selection. Each system's `template.json`
owns its metadata; both catalogs are generated views. Read only shortlisted
recipes, then the selected `design.md` and available layout/token resources.
There is no need to read every design file.

## Fit the difficult material

Match the audience and argument using `best_for`, `avoid_for`, `tone`, `density`
and `visual_signature`. Then test `supported_layouts` against the actual forms:
comparison, chart, table, mechanism, product sequence or dense reading page.
`weak_cases` describes composition limits that the mood of a cover will not
reveal. `assets` names fonts, font delivery and imagery needs;
`language_posture` describes adaptation limits, not verified glyph coverage.

`maturity` distinguishes a recipe, preset, starter or developed system. A starter
may offer good tokens and direction while leaving real content layouts to build.
It is not a failed developed system, and its existence is not evidence that all
slide forms have been exercised. Safe, bold and house families identify source
provenance; they do not rank fitness, quality or completeness.

Build or inspect a representative difficult slide early. An institutional
template may fit a board audience yet fail a detailed financial table; an
expressive recipe may be appropriate for a reveal but unhelpful for options
with many qualifications. Adapt the selected system or build a custom one when
that serves the material better. Never alter evidence or suppress qualifications
to make a template look successful.

## Choose or compare

When the user names a system or the task gives a clear direction, proceed with
it unless a concrete conflict needs discussion. Otherwise make a professional
choice within the mandate. Render alternatives when uncertainty about taste or
fit is worth resolving, or when the user requests them; there is no fixed count,
safe/bold/wildcard quota or required three-cover gallery.

Useful comparisons show the same content-bearing slide in materially different
visual treatments. Add a cover only when it exposes a relevant choice. A
style-only comparison preserves title, thesis, audience, claims, evidence,
qualifications, sequence and ask. If alternatives change the argument, label
them as narrative exploration and update the semantic source deliberately.

Keep gallery labels outside slide frames. The slide itself contains real deck
content, never template names, slugs, option labels, source paths or copied demo
copy. Preserve meaningful content labels and source citations. Internal proof
and publication workflow language belongs in backstage notes, not decoration.

Translate recipes using viewport units into the canonical 1920×1080 stage.
Choose fonts for the actual language and verify their rendered glyphs. Before
release-bound proof, resolve allowed external fonts and images to local or
inline bytes; catalog metadata does not establish that dependencies were loaded.
